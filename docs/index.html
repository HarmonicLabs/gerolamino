Install Gerolamino as a browser extension

Gerolamino is a local chain reader, not a wallet. It keeps no keys and cannot sign. It needs a Gerolamo peer that serves N2N-over-WebSocket; Gerolamo itself is a full node, Gerolamino is the browser light node.

Supported browsers: Chrome 116+ or Brave (MV3, offscreen document). The extension is loaded unpacked today; there is no Chrome Web Store listing in this repository.

1. Before you start

  • Bun 1.1+ and git are installed.
  • You have a relay URL: ws://host:port/n2n or wss://host/n2n. A Gerolamo peer must listen on that WebSocket and serve the matching network magic. Ports are flags on Gerolamo, never environment variables.
  • If you do not have a relay yet, run Gerolamo locally first: RUN_LOCAL_GEROLAMO.md. The default setup there gives ws://127.0.0.1:3004/n2n.
  • Pick the network at the relay: preview (magic 2) or preprod (magic 1). Gerolamino settings offer those two; mainnet (magic 764824073) is deferred on the browser side.

2. Build the extension

git clone https://github.com/HarmonicLabs/gerolamino.git
cd gerolamino
bun install
bun run build

bun run build writes the unpacked MV3 extension to dist/. The build also regenerates manifest.json and the icons; do not load src/extension/ directly, it has no bundled JavaScript.

3. Load it in Chrome or Brave

  1. Open chrome://extensions (Chrome) or brave://extensions (Brave).
  2. Turn on Developer mode.
  3. Click Load unpacked and select the dist/ directory of the Gerolamino checkout.
  4. Pin Gerolamino to the toolbar if you want the popup one click away.
  5. The extension id is assigned by the browser on load; do not hard-code it in a dApp.

4. Configure the relay

  1. Click the Gerolamino icon, then open Settings in the popup.
  2. Network: preview for the local Gerolamo preview setup.
  3. Relay URL: ws://127.0.0.1:3004/n2n for Gerolamo on the same machine. Replace host and port for a remote relay, for example ws://relay.example:3004/n2n or wss://relay.example/n2n.
  4. Start mode: tip on a first run. chunk starts from the relay's newest complete chunk, mithril from the certified Mithril point. A stored tip wins when resuming.
  5. Save. Settings live in chrome.storage.local; only Gerolamino's own pages can read them.

Extra relays are optional, must use the same network, and are capped at four. They cross-check the main peer's headers; Blockfrost queries fail over only.

5. Verify the first start

  • Popup Relay shows the peer's tip; N2N shows the handshake version and whether light query is available.
  • Blocks stored and Ledger UTxO grow after the first block is verified. Trust shows local UTxO coverage or a stale warning.
  • The popup Storage card shows immutable chunks, volatile files and the ledger row.
  • Health checks outside the browser (replace port with the Gerolamo --port; Docker compose uses 3030): 
    curl -s http://127.0.0.1:3037/health | jq .
curl -s http://127.0.0.1:3037/api/v0/ | jq '{version, endpoints}'
    (replace the port with the Gerolamo --port value).

If it does not connect, check in this order: the URL starts with ws:// or wss:// and ends in /n2n; the relay host is reachable; Gerolamo was started with --n2n-ws and the port matches; network magic is the same; the firewall or TLS proxy is not blocking WebSocket upgrades. HTTP is not the relay: Gerolamo's HTTP API is only for the mini-Blockfrost fallback.

6. Reload after a rebuild

bun run build

Open chrome://extensions, find Gerolamino, and click Reload. Stored chain, ledger and settings survive a reload. To start clean, use the popup's wipe action; it removes immutable chunks, volatile files and the local UTxO ledger for the selected network, then the node syncs again from the relay.

7. dApps and the Blockfrost adapter

A page sees window.cardano.gerolamino (apiVersion: "1", dappApiVersion: "0.1.0", isWallet: false). The extension asks for approval per site and rate-limits queries. The Blockfrost SDK adapter is built as dist/gerolamino-blockfrost.js; see DAPP_API.md and BLOCKFROST_THROUGH_GEROLAMINO.md.

For local testing, bun scripts/serve-demo.ts serves the demo at http://127.0.0.1:8787/. The e2e harness loads an unpacked build itself:

bun scripts/e2e-chrome.ts --chrome /usr/bin/brave-browser --relay ws://127.0.0.1:3004/n2n --start chunk

8. Limits

Gerolamino verifies headers and block bodies, stores the verified chain, and answers UTxO queries with local coverage. It does not sign, does not hold keys, and does not perform full ledger-rule/consensus parity yet (P0 UTxO projection, coverage-first answers; P1/P2/P3 in LEDGER_SPEC.md).

Run a local Gerolamo relay

Docker and Bun options for the Gerolamo node that serves Gerolamino over N2N-over-WebSocket.

Open raw Markdown Jump to section

Run Gerolamo locally as Gerolamino's relay

Gerolamino's default relay is now ws://127.0.0.1:3004/n2n: Gerolamo on the same machine. For a remote relay, replace host and port; use wss:// when TLS is terminated in front of the WebSocket port.

Gerolamo reads no environment variables. Every setting is a CLI flag or a config.json key. A flag wins over the network config; see Gerolamo's docs/CONFIG.md for the full list.

Prerequisites

  • Bun 1.1+, git, and a writable data directory.
  • Preview is the current pilot network (magic 2). Preprod is magic 1. Mainnet is magic 764824073, but the Gerolamino extension currently offers preview and preprod only.
  • Gerolamo needs disk and time for its first snapshot or genesis sync; the preview pilot is the tested path.

Option A: Docker (recommended for a self-contained relay)

git clone https://github.com/HarmonicLabs/gerolamo.git
cd gerolamo

Gerolamo's bundled docker-compose.yml starts a preview relay from a Mithril snapshot. Gerolamo flags are passed in the compose command: list, and node flags go after --. Add WebSocket to the existing command:

    command:
      - --network
      - preview
      - --port
      - "3030"
      - --bootstrap
      - mithril
      - --role
      - relay
      - --max-rss-gb
      - "8"
      - --
      - --n2n-ws
      - --n2n-ws-port
      - "3004"

Expose the HTTP API and WebSocket port on the host:

    ports:
      - "127.0.0.1:3030:3030"
      - "127.0.0.1:3004:3004"

For relay access from another machine, bind 0.0.0.0 and open the ports deliberately:

      - "3004:3004"

Docker's first start downloads and verifies the Mithril snapshot; later starts resume from the mounted ./data/preview directory. Start and verify:

docker compose up -d --build
docker compose logs -f gerolamo       # first bootstrap takes a while; wait for /health
curl -s http://127.0.0.1:3030/health | jq .
curl -s http://127.0.0.1:3030/api/v0/ | jq '{version, endpoints}'

Gerolamino relay URL: ws://127.0.0.1:3004/n2n. Mini-Blockfrost fallback for Bun/backend code: http://127.0.0.1:3030/api/v0/*.

Option B: Bun directly (developer setup)

git clone https://github.com/HarmonicLabs/gerolamo.git
cd gerolamo
bun install
DATA="$PWD/data/preview"; mkdir -p "$DATA"

Bootstrap the ledger and block store once (Mithril snapshot; later starts resume):

bun src/index.ts mithril-bootstrap --network preview \
  --download-dir "$DATA/snapshots" \
  --block-store "$DATA/db" \
  --ledger-state --ledger "$DATA/ledger" \
  --db "$DATA/preview.db"

Create "$DATA/local-config.json" next to the data (absolute paths work best):

{
    "role": "relay",
    "ledgerStore": "lmdb",
    "ledgerSqlWrites": false,
    "ledgerDir": "/absolute/path/to/data/preview/ledger",
    "blockStoreDir": "/absolute/path/to/data/preview/db",
    "relayStore": "chunks",
    "n2n": { "enabled": true, "host": "127.0.0.1", "port": 3001 }
}

Start the node with its HTTP port and WebSocket bearer:

bun src/index.ts start-gerolamo --network preview \
  --port 3037 \
  --db-path "$DATA/preview.db" \
  --config "$DATA/local-config.json" \
  --n2n-ws \
  --n2n-ws-port 3004 \
  --n2n-ws-host 127.0.0.1

Optional TCP node-to-node listens on n2n.port (3001 in the example) for ordinary Gerolamo peers; the WebSocket listener is the one Gerolamino uses. For a LAN relay, set --n2n-ws-host 0.0.0.0 and use the machine's address in the extension. Keep one writer per database; choose a unique HTTP/WS port per instance.

Verify:

curl -s http://127.0.0.1:3037/health | jq .
curl -s http://127.0.0.1:3037/api/v0/ | jq '{version, endpoints}'
ss -ltnp | grep -E ':3037|:3004'

Gerolamino then uses:

Relay URL: ws://127.0.0.1:3004/n2n
Mini-Blockfrost fallback: http://127.0.0.1:3037/api/v0/*   (Gerolamo HTTP, not the relay)
Network: preview

Port map in the docs

PurposeGerolamo settingExample
HTTP API, dashboard, mini-Blockfrost--port3037
N2N-over-WebSocket--n2n-ws-port3004
Ordinary N2N TCP--n2n-port3001
N2C unix socket (optional)--n2c-socket./node.socket

--n2n-ws must be enabled for Gerolamino. The WebSocket path is /n2n; Gerolamo also accepts /relay and /. Only ws:// or wss:// URLs are valid in the extension.

Remote access and TLS

For a relay elsewhere, use its DNS name or address, not a hard-coded address from an example:

ws://<relay-host>:<n2n-ws-port>/n2n
wss://<relay-host>/n2n

Terminate TLS at a reverse proxy in front of the Gerolamo WebSocket port and keep the relay on the matching network magic. A public deployment should rate-limit, monitor /metrics, and keep the node current.

Troubleshooting

  • ws:// URL fails: confirm Gerolamo was started with --n2n-ws and --n2n-ws-port; check ss and /health.
  • Wrong network: preview is 2, preprod is 1; the extension setting and the Gerolamo --network must agree.
  • 127.0.0.1 fails from another machine: it means loopback on that machine; use the LAN/host name.
  • HTTP endpoint fails but relay works: the mini-Blockfrost is on the node's --port, not the WebSocket port.
  • First sync is slow: Docker/Bun uses the Mithril snapshot; a fresh preview genesis sync is expected to take much longer. Check Gerolamo logs and /metrics rather than assuming the relay is broken.

Gerolamino dApp API

window.cardano.gerolamino lets a web page use the visitor's own Cardano node. It follows CIP-30 conventions: injection under window.cardano, one enable() approval per site, CBOR hex and the same error objects. Gerolamino holds no keys, so it is not a wallet: it reads the chain for the page, says how each answer was verified, and submits transactions a wallet already signed.

Connecting

const node = window.cardano?.gerolamino;   // undefined: Gerolamino is not installed
await node.isEnabled();                    // false until the user allows this site
const api = await node.enable();           // opens Gerolamino's "Allow this site?" window once

enable() rejects with { code: -3, info } when the user denies or closes the window. The user can remove the site later in Gerolamino's Settings ("Connected sites"); calls then fail with code -3 until enable() is called again.

Methods

query(path){ status, body, source, peer, proof, ledger }any Blockfrost GET, path under /api/v0 ("/blocks/latest"); ledger is { startSlot, kind, tipSlot } on local UTxO answers
getUtxos(address)as query/addresses/{address}/utxos

Where an answer comes from

query answers carry source:

  • "local": from blocks this node verified and stored itself (/blocks/latest, /blocks/{id}, /blocks/{id}/txs, /txs/{hash} for stored blocks), or from its local UTxO ledger (/txs/{hash}/utxos, /utxo/{txhash:index} while coverage covers the transaction and is not stale; /addresses/{addr}/utxos only at genesis/snapshot coverage 0). Local UTxO answers carry ledger: { startSlot, kind, tipSlot }, the slot their state is complete from.
  • "relay": from a Gerolamo peer that answers from its full ledger (peer names it). The main relay is asked first; when it cannot answer (no light query, timeout, 5xx), an extra Gerolamo peer that supports Blockfrost queries answers instead, honouring that peer's announced rate limit. A peer that announces capabilities without blockfrost is never asked. For /txs/{hash}… the node also asks Mithril for a proof that the transaction is on the chain, and proof.status is "certified" (with the certified block range), "too-new", "mismatch" (the peer is wrong) or "unavailable". A stale or partial local ledger relays instead of inventing UTxO; /addresses answers relay unless coverage starts at 0.

status and body are Blockfrost's: a 404 is { status: 404, body: { status_code: 404, … } }, not an error.

Errors

CIP-30 objects { code, info }:

CodeMeaning
-1InvalidRequest: unknown method or bad arguments
-2InternalError: the node failed (for example no verified block yet)
-3Refused: the site is not allowed, the user denied it, or the site called too often (60 calls per 10 s)
1, 2submitTx only, TxSendError Refused or Failure

Security

  • The site's origin is taken from the browser (the content script's sender), never from the page.
  • Web pages can only reach the dApp calls; settings, the store and approvals are for Gerolamino's own pages.
  • Only http and https pages get the API.

Try it

bun scripts/serve-demo.ts          # http://127.0.0.1:8787/

Open the page with the extension loaded, press Connect and allow the site. The browser test drives the same page: bun scripts/e2e-chrome.ts --chrome /usr/bin/brave-browser --relay ws://127.0.0.1:3039/n2n --dapp.

Blockfrost through Gerolamino (in the browser)

Gerolamino is the browser-side Blockfrost gateway: a page does not call window.fetch against a Blockfrost proxy; it asks the extension, which answers from its own verified store first and otherwise forwards the request to the Gerolamo peer it is connected to (N2N-over-WebSocket light query, request 8, mini-Blockfrost backend). If the main relay cannot answer, an extra Gerolamo peer that supports Blockfrost queries answers instead (the answer's peer names it, per-peer announced rate limits honoured). No project_id, no CORS, no API key; the chain comes over the same socket the node already follows.

What a page gets

window.cardano.gerolamino.enable() (one approval per site origin) returns an api with:

  • query(path) → { status, body, source: "local" | "relay", peer, proof, ledger } for any Blockfrost GET path (/blocks/latest, /epochs/latest, /addresses/{addr}/utxos?count=100&page=1, /txs/{hash}/utxos, /utxo/{txhash:index}, /txs/{hash}/metadata, /assets/policy/{policy}, ...). ledger is { startSlot, kind, tipSlot } on local UTxO answers.
  • submitTx(txCborHex) → tx id (a wallet-signed transaction; Gerolamino never signs).
  • getTip(), getTrust(), getNetworkId(), getUtxos(address), getAccount(stake), getProtocolParameters().

Limits: 60 calls per 10 s per origin; query paths start with /, max 1024 chars, no ..; relayed transaction answers carry Mithril proofs when the setting is on.

The provider adapter

src/dapp/blockfrostProvider.ts (built to dist/gerolamino-blockfrost.js) wraps that api in the shape an SDK provider expects:

import { enableGerolamino, gerolaminoProvider, hasGerolamino } from "./gerolamino-blockfrost.js";

if (hasGerolamino()) {
    const api = await enableGerolamino();              // approval window once per site
    const provider = gerolaminoProvider(api);          // hand this to the SDK instead of window.fetch
    const tip = await provider.json("/blocks/latest");
    const utxos = await provider.getAllPages("/addresses/" + addr + "/utxos");  // pages of 100, stops on a short page
    const txid = await provider.submitTx(signedCborHex);
}

gerolaminoFetch(api) gives a fetch-shaped (url) => {status, body, source} for SDKs that call a fetch function internally; it strips /api/v0 from full URLs. provider.get(path, {count, page, order}) is the paged GET; provider.json throws on non-200.

When to use it

  • Browser dApp with Gerolamino installed and connected: use the adapter; reads are local-first (stored block facts and local UTxO answers with coverage), then relay-backed, and the page never needs the Gerolamo HTTP port. A stale or partial local ledger relays rather than inventing UTxO.
  • Bun/backend/CI: use the Gerolamo mini-Blockfrost over HTTP on the node's --port (http://127.0.0.1:3037/api/v0/* for a local node, or http://<node-host>:<http-port>/api/v0/*); the adapter needs window.
  • Fallback: if hasGerolamino() is false (extension absent), keep the OnchainApps/Blockfrost provider; the adapter is additive, not a replacement.

Proof

bun test test/blockfrostProvider.test.ts (4 tests: detection/enable, paged GET + error mapping, getAllPages, submitTx + fetch shape). Live: bun scripts/adapter-smoke.ts (Brave headless, the real extension, the Gerolamo peer): provider.json("/blocks/latest") local 200 (preview height 4,803,xxx), get("/epochs/latest") relay 200 (epoch 1464), getAllPages("/addresses/{addr}/utxos") relay 200 (9 UTxOs across 2 pages), get("/blocks/1000") relay 200. bun scripts/e2e-chrome.ts --dapp drives the same api in Brave (query("/blocks/latest") → 200 local, query("/epochs/latest") → 200 relay, allow/deny per site). The ledger P0 e2e (--start chunk) additionally proves query("/txs/{hash}/utxos") and query("/utxo/{ref}") answer locally with ledger: { startSlot, kind, tipSlot } and resume the diff log after the offscreen document is recreated.

Architecture

Local ledger specification

P0 UTxO projection, coverage, digest chain, resume and rollback.

Open raw Markdown Jump to section

Gerolamino local ledger (implemented P0, 2026-10-29)

Status: P0 implemented and proven; P1 snapshot import and local compaction implemented 2026-10-30 (local files, streaming decoder, signed ancillary manifest check, full preview count 3,169,305 entries). The aggregator download/UI is the remaining P1 wiring. This closes the local ledger part of Milestone 4 ("Browser adaptation and light node on the browser"): Gerolamino verifies and stores blocks, and now maintains its own UTxO projection in OPFS instead of taking UTxO from a Gerolamo peer.

Scope and boundaries

  • Local UTxO set. The node maintains its own UTxO state in OPFS, updated from blocks it verified itself. It never takes ledger state from a peer without proof.
  • Coverage is first-class. Every local ledger answer states the slot from which its state is complete. A tip/chunk/Mithril start gives coverage startSlot; only a genesis or snapshot bootstrap gives coverage 0.
  • Light node, not consensus. Header/body verification stays as it is. Phase-2 script execution, stake, governance, epoch rewards and full ledger rule validation are P2/P3; the UTxO projection says so.
  • Pure TypeScript on HarmonicLabs. Parsing uses @harmoniclabs/cardano-ledger-ts (pinned vendor tarball), storage uses the existing OPFS sink pattern; no SQLite, no LMDB, no Bun-only APIs in the extension.
  • No keys. The ledger never signs, validates scripts, or becomes a wallet.

Coverage model (implemented shape)

interface LedgerCoverage {
  network: string;
  startSlot: number | null;              // first verified block applied; null before any block
  kind: "verified-start" | "snapshot" | "genesis"; // P0 always "verified-start"
  tipSlot: number | null;
  blocks: number;
  utxoCount: number;                     // unspent only
  digest: string | null;                 // blake2b-256 chain of per-block diffs
  stale: boolean;                        // a gap or a failed digest/write
}
  • genesis: complete from slot 0 (only after a genesis replay or snapshot import).
  • snapshot: complete from a Mithril-certified snapshot slot (UTxO base imported, later blocks applied).
  • verified-start: the node started at tip/chunk/Mithril; UTxO state covers only outputs seen since that slot. /addresses answers relay unless coverage starts at 0 or the base is a snapshot.
  • A rollback moves tipSlot back but never moves startSlot; if a rollback crosses the start, the ledger reports the gap (stale or partial) and does not pretend completeness.

Data model

  • UtxoRef = txid(hex):index(u16). LedgerOut: { ref, txHash, address, addressBytes, lovelace, assets: Array<{ policy, name, quantity }>, datumHash?, inlineDatum?, scriptRefHash?, stakeKey?, createdSlot, spentSlot: number | null }.
  • Spent outputs stay as tombstones in memory (needed for rollback and tx lookups); local compaction keeps them in the base snapshot, so a snapshot base remains query-compatible.
  • In-memory indexes: utxos: Map<ref, LedgerOut> (spent included), byAddress: Map<address, Set<ref>>, byTx: Map<txHash, { out: ref[]; input: ref[] }>, stakeBalance: Map<credential, bigint> (kept, not yet queried). The address is the bech32 string produced by ledger-ts; raw address bytes are kept for stake keys.
  • Transaction facts stay in localIndex.ts; the ledger adds UTxO views rather than duplicating block facts.
  • Block diff (LedgerBlockDiff): format: 1, slot, hash, txs, invalidTx: number[], created: LedgerOut[], spent: ref[]; per stored diff also prevDigest, digest, unknownInputs (the compiler records unknown inputs there).

Storage layout (OPFS, implemented)

gerolamino/<network>/ledger/
  manifest.json                       # coverage, tip, counters, digest chain, format 1, written last
  snapshot.json                       # P1 base at a slot: UTxO rows + spent tombstones + counters (optional)
  b-<10-digit slot>-<hash8>.ldiff     # one verified block newer than the base: created/spent diff + digest chain

  • snapshot.json is the base under the per-block diff log. It carries format, network, original startSlot, coverage kind, slot, chain digest, state stateDigest, cumulative counters and historyComplete (true for local compaction, false for a Mithril tables import). Resume reads it once and replays only diffs newer than its slot.

  • File name: b-${slot.padStart(10)}-${hash.slice(0,8)}.ldiff (flat directory, no blocks/ subdir).

  • The single writer is BrowserNode through the OPFS worker; manifest.json is written after each diff.

  • Resume: read the manifest, then replay every diff in slot order, checking prevDigest continuity; a missing diff, a missing manifest with diffs present, a corrupt diff, a tip mismatch or a digest mismatch marks the ledger stale rather than failing half a block. The ledger loads what it can and refuses local answers while stale.

  • Rollback within the volatile window: reverse diffs newer than the target slot in bulk (spent outputs become unspent again, created outputs leave, counters rebuild), delete their files, rewrite the manifest. Local compaction treats the snapshot slot as a base; rolling back below it marks the ledger stale and keeps the snapshot state (a deeper rebuild is future work).

  • Compaction (compactTo(slot)): write the UTxO state at slot as snapshot.json (spent tombstones included, original startSlot kept), drop every diff file at or below slot, then re-apply the newer diffs on top of the base. A rollback below the snapshot slot never pretends to reconstruct the missing history.

  • A write failure reverts the in-memory diff, removes the file and throws; BrowserNode catches it, marks the ledger stale and keeps the verified chain store intact. A decode failure likewise marks stale, never drops a chain block.

  • Wipe (wipe-store) removes immutable, volatile and ledger together; the next start rebuilds coverage from the first verified block.

Bootstrapping

Snapshot import (P1, implemented for local files): verify the signed ancillary_manifest.json (Gerolamino's 64-bit SHA-256 of tables/meta, network ancillary Ed25519 key), stream-decode entries with the MemPack decoder, build the UTxO-only base snapshot (historyComplete: false), install it under the ledger dir, then apply blocks from the snapshot slot onward. The aggregator/peer download and the UI switch are the remaining P1 wiring. A tampered manifest or table fails before any ledger state is written.

Block application (P0 UTxO projection, implemented)

Input: a verified block's bytes, slot, hash and invalidTransactions flags (body parser). Per transaction, in block order:

  1. If marked phase-2 invalid: spend only its collateral inputs; create no ordinary outputs; record the tx index in invalidTx; a collateral return is created at index outputs.length (same rule as Gerolamo).
  2. Otherwise: spend regular inputs; add outputs (all eras that have Babbage-shaped outputs); reference inputs are not spent by ordinary inputs.
  3. Same-block spends are allowed in the order transactions appear; an input not in the local UTxO is recorded in that block's unknownInputs and removes nothing (coverage gap, not a block failure).
  4. Update address/stake indexes and balances; keep tombstones for spent outputs.
  5. Compute the diff digest: blake2b-256(prevDigestBytes ‖ JSON({slot, hash, created refs, spent, unknown, invalid})); store the diff, then the manifest.

What P0 does not do: phase-2 script execution, fee/deposit/balance checks, stake delegation effects, governance, epoch rewards, Byron payload-ledger effects. These are P2/P3 work; queries must state it.

Rollback: reverse a block diff in memory (unspend, delete created, restore balances/counters) and delete its diff file. A deeper rollback than the retained diffs rebuilds from the newest snapshot (P1).

Failures: an undecodable body marks the ledger stale at that block (the chain store keeps going; later diffs can still append, but local UTxO answers relay until a rebuild). A result it could not decode is never written as a partial diff.

Trust and consistency rules

  • Ledger state derives only from blocks this node verified; no peer-supplied UTxO entries enter the store.
  • The digest chain is recomputed after every applied block; a resume/diff mismatch marks the ledger stale and local answers stop until a rebuild.
  • Unknown inputs are recorded per block and shown in stats; partial coverage answers carry coverage metadata and never claim genesis completeness.
  • Snapshot bootstrap is "certified by Mithril" only after the existing anchor/certificate/Merkle checks; the ancillary file's own signature is verified separately.
  • Never claim full consensus validation, full address history, or UTxO from genesis unless coverage says so.

N2N over WebSocket: what Gerolamino needs from a peer

This page is the working basis for a CIP that lets any Cardano node serve browser nodes. The draft itself is in the Gerolamo repository, CIP/n2n-over-websocket/README.md. It describes what Gerolamino does as a client today and what Gerolamo does as a server. The open questions at the end are what the CIP still has to settle.

Transport

  • Connection. A WebSocket (RFC 6455); wss:// in production, through TLS at the node or a reverse proxy.
  • Payload. Binary messages only. The concatenation of all message payloads in one direction is exactly the byte stream a TCP N2N peer would send: Ouroboros multiplexer segments, each an 8-byte header plus up to 65 535 payload bytes.
  • Message boundaries. Senders should put whole segments in each message. Receivers must accept a segment split across messages, and several segments in one message, as with TCP.
  • No subprotocol. None is negotiated today; the CIP may define one (see the open questions).

Endpoint

PathStatus
/n2ncanonical on Gerolamo
/accepted by Gerolamo
/relayaccepted by Gerolamo, because the first Gerolamino build always appended it

Other paths get HTTP 404. The server rejects the upgrade with HTTP 503 when it is at its connection limit.

Mini-protocols

The same N2N protocols, numbers and state machines as over TCP:

NumberProtocolGerolamino
0handshakeuses
2chain-syncuses
3block-fetchuses
4tx-submissionuses
8keep-aliveuses
10peer-sharingdoes not use
7light queryGerolamo extension, used

Light query is a Gerolamo extension for the epoch nonce, pool stake, immutable chunk files and, since 2026-10-23, read-only Blockfrost queries ([8, id, path] → [9, id, status, json], answered by the peer's own Blockfrost API; GET only, 30 per 10 s per peer, answers up to 512 KiB). Gerolamino answers what its stored blocks contain itself and asks the peer for the rest (ledger state, blocks before its start point). A peer without request 8 answers [255]. With it, a browser node can verify headers and start from a Mithril-certified chunk without a second channel. Whether it belongs in the CIP is an open question.

Handshake

  • Versions. The client proposes N2N v14 and v15; the server answers with the highest common version.
  • Initiator-only. A browser cannot accept connections or serve the chain, so the client sets initiatorOnlyDiffusionMode: true and peerSharing: 0. The server must not start initiator protocols toward it.
  • Server side. Gerolamo answers WebSocket peers with initiatorOnlyDiffusionMode: true, so neither side expects duplex use.

Liveness

  • Client. Gerolamino sends keep-alive every 20 s or less. A Chrome MV3 extension also needs traffic at least every 30 s to keep its service worker alive.
  • Server. Gerolamo closes a connection idle for 120 s, and its own outbound sessions close when a keep-alive reply is overdue for 60 s.

What a browser node needs from the server

  • Chain-sync. Headers from genesis or from a recent point.
  • Block-fetch. Ranges of blocks.
  • A way to verify headers. The epoch nonce and pool stake; today via light query.
  • A trusted start. A complete immutable chunk to start from, which can be checked against a Mithril certificate; today via light query, or HTTP from the Mithril aggregator for the certificates.

Decided for the CIP: service announcement (2026-10-23)

Optional services are announced, never probed, and never in the N2N handshake's version data.

  • Why not the version data. For N2N v14/v15 it is a fixed record (network magic, initiator-only, peer sharing, query); cardano-node decodes it strictly, so an extra field breaks the handshake, and changing it needs a new N2N version in ouroboros-network.
  • Why not probing. A node's multiplexer may drop the connection on traffic for a mini-protocol it does not run, so a client must know before it sends on the light-query protocol.
  • Layer 1, at connection setup: the WebSocket subprotocol. The client offers, best first, Sec-WebSocket-Protocol: cardano-n2n.v1+lightquery, cardano-n2n.v1; the server selects the richest it supports. A plain N2N node (cardano-node or Dingo behind a proxy) selects cardano-n2n.v1: standard protocols only. The browser reads the choice from ws.protocol before any N2N byte, and it is the only response detail browser JavaScript can see. A server that selects nothing is treated as standard-only.
  • Layer 2, inside the light query: capabilities in the hello. [4] → [5, magic, version, capabilities], where capabilities lists the request types the peer serves and their limits (nonce, stake, chunks, Blockfrost queries with rate and answer size). Clients ask only for what is listed.
  • Discovery uses the same names. The record that tells browsers where WebSocket relays are lists the same services, so a browser can choose peers before connecting: standard-only peers for chain-sync, block-fetch and cross-checking; light-query peers for nonce, stake, certified starts and ledger queries.

Open questions for the CIP

  1. Path. One canonical path (/n2n?), or discovery?
  2. Subprotocol. A Sec-WebSocket-Protocol name, for example cardano-n2n.v1, so servers can refuse unknown clients cleanly.
  3. Discovery.
    • Pool relay registrations carry IP, DNS or SRV for TCP only.
    • Options: a field in extended pool metadata, an SRV record convention, or peer-sharing extended with a WebSocket address type.
  4. Light query. Standardise nonce and stake (and chunk) queries as a mini-protocol, or require a separate HTTP API?
  5. Browser limits.
    • Origin checks: servers should not rely on them.
    • Connection caps per IP.
    • Range limits for block-fetch.
  6. Back-pressure. Whether to cap in-flight bytes per WebSocket, since browsers buffer without bound.

Gerolamino status (2026-10-16, ledger P0 added 2026-10-29)

Gerolamino is a standalone Cardano node for the browser, shipped as a Chrome MV3 extension. This page records why it was rebuilt, what works, what was measured, what is missing, and the problems found in the libraries it depends on.

Role and scope (2026-10-22)

Gerolamino is the light member of the Gerolamo family, not a smaller copy of all of it.

  • What it is. A data and information node: it follows the chain, verifies what it receives, keeps it in OPFS and answers questions about it. It may later act as a relay for other browser peers.
  • What it is not. It will never host a stake pool. Block production, KES keys and leader schedules stay in Gerolamo.
  • Default use. Most people will sync from the tip. That path must stay fast, small and dependable. Starting from an immutable chunk or a Mithril-certified point are welcome extras, never requirements for the default path; the local UTxO projection (P0, 2026-10-29) runs on every path and carries its coverage.
  • Relay default (2026-10-29). The default relay URL is ws://127.0.0.1:3004/n2n, meaning Gerolamo on the same machine. Setup: docs/RUN_LOCAL_GEROLAMO.md; extension load: docs/INSTALL_EXTENSION.md. The historical 192.168.1.173:3004 evidence below is a reference deployment, not a requirement.
  • Look and feel. The UI follows Gerolamo's desktop app (Electrobun, gerolamo/desktop), simpler and lighter: same dark theme, red-to-orange accent, cards, progress ring and badges. It does not follow the old web dashboard. Gerolamino builds it in plain TypeScript and CSS, because it takes no third-party runtime packages (no Solid, no Tailwind).

Why it was rebuilt

The first Gerolamino (HarmonicLabs/gerolamino main, May 2026) was an Effect v4 monorepo. It used Haskell lsm-tree compiled to WebAssembly with GHC's WASM backend for storage, and Rust crates compiled to WASM for the multiplexer and crypto. It reached peers through a websockify proxy in front of a cardano-node relay.

On 2026-10-16 we ran it against Gerolamo's native N2N-over-WebSocket bearer:

  • Network: worked. Handshake (version 15), intersection, rollback, and 6 215 blocks streamed in three minutes.
  • Storage: failed. Every block write failed inside its WASM LSM store, whose session never opened in genesis mode.
  • Before that, a silent stop. Effect API drift stopped the sync before the socket opened: a renamed timeoutOrElse option threw.
  • Build. The storage layer can only be built through Nix and the GHC WASM toolchain.

The decision was to rebuild it in pure TypeScript on the HarmonicLabs libraries, with no Haskell, no WASM, no Effect and no third-party runtime packages, and the chain kept in OPFS. Gerolamino stays its own codebase. It does not import Gerolamo; the pieces it shares in spirit (chunk format, header checks, Mithril verification) are ported and owned here.

Volatile store (2026-10-28)

Blocks within k slots of the tip are no longer written into the immutable chunk files. They live in gerolamino/<network>/volatile (one v-<slot>.blk file per block, header hash + block bytes) and are promoted to the chunk writer only when they are k slots behind the tip (promoteOlderThan(h.slot - k)). A rollback inside the k window therefore truncates volatile files only; chunk files are rewritten only when a rollback crosses the k boundary. Resume reads the chunks first, then the volatile store, and starts at the volatile tip when it is newer. Files under the volatile path: at most about k slots of blocks.

Live (Brave, scripts/e2e-chrome.ts --start chunk --relay ws://192.168.1.173:3004/n2n, 2026-10-28): PASS. The immutable directory held one chunk (29295), the volatile store the newer blocks; after closing and recreating the offscreen document the node resumed at the volatile tip (126555200) with no block lost (34 stored before, 36 after), and the popup showed 41 blocks with tip slot 126555407.

Peer-backed Blockfrost queries (2026-10-28)

A Blockfrost GET the local index cannot answer goes to the main relay first. When that peer cannot answer (no light query, timeout, connection closed, 5xx, or an announcement without blockfrost), the query fails over to an extra Gerolamo peer that speaks the light query: peers that announce blockfrost come first, version-0 peers (no announcement) are probed last, and each peer's announced rate/window is honoured (a rate-limited peer is skipped, not failed). The answer names the peer that actually answered (peer), and a 503 is returned only when no peer answers. Code: src/node/queryRouter.ts; runner candidates: main node first, then watchers (src/node/runner.ts queryCandidates).

Live (Bun, scripts/query-failover-smoke.ts, 2026-10-28): main relay ws://127.0.0.1:9999/n2n dead, extra ws://192.168.1.173:3004/n2n: /addresses/{addr}/utxos 200 (peer ws://192.168.1.173:3004/n2n), /epochs/latest 200 (epoch 1465), /blocks/1000 200 (height 50). PASS.

Local UTxO ledger (2026-10-29)

Every verified block feeds a local UTxO ledger in gerolamino/<network>/ledger: one b-<10-digit slot>-<hash8>.ldiff file with created outputs, spent inputs (collateral only for phase-2 invalid transactions), unknown inputs and a digest chain, plus a manifest.json written last. Speed

Header checks cost about 110–170 ms in Bun and 180–290 ms in Chrome. The default ed25519 and VRF in @harmoniclabs/crypto are BigInt implementations at 40–65 ms per operation. That is fine at the tip and slow from genesis, about 8.6 headers/s.

The fix stays inside the HarmonicLabs libraries. @harmoniclabs/crypto ships a strict port of noble's ed25519 under dist/noble/ed25519.js that verifies in about 1 ms; Gerolamo's header validation already uses it. The VRF can be rebuilt on the same curve code.

Not done

  • Full ledger rules (fees/deposits, stake delegation, governance, epoch rewards) and phase-2 script execution are P2/P3; P0 is a UTxO projection with coverage only.
  • P1 snapshot base is from local files only: signed ancillary manifest check, streaming MemPack decoder and snapshot.json; the aggregator/peer download and UI start mode are still missing. /addresses answers relay when no snapshot base is installed.
  • The ledger diff set above a snapshot base is compacted on demand (compactTo); there is no automatic compaction threshold yet.
  • OPFS ledger retries after a stale marker rebuild from the first verified start or the snapshot base.
  • The epoch nonce is confirmed, not computed: computing it needs the whole previous epoch's headers.
  • No preprod run yet; there is no preprod Gerolamo relay.
  • Real signed transaction submission is untested.
  • Byron headers are not verified; Byron payload-ledger effects are outside P0.
  • Session counters reset when the offscreen document is recreated (the ledger survives in OPFS).

Problems found in the HarmonicLabs libraries

Each is pinned by a test here and worked around in Gerolamino's own code.

  1. @harmoniclabs/crypto 0.3.1, ed25519 (verifyEd25519Signature_sync).
    • Forgery. With the identity public key (01 00…00), the signature R = identity, S = 0 verifies for any message.
    • Too lenient. It accepts S + ℓ (malleable), non-canonical point encodings, and small-order keys and R.
    • Bad lengths. It throws instead of returning false.
    • Wrong typings. verifyEd25519Signature is typed with the argument order (publicKey, signature, data), but runs the sync function (signature, message, publicKey).
    • Workaround here. Gerolamino uses a strict check with dalek verify_strict semantics. Gerolamo's header path uses the bundled noble port and is not exposed.
  2. @harmoniclabs/crypto 0.3.1, VRF. VrfProof03.verify accepts a non-canonical response scalar (s + ℓ), which libsodium rejects.
  3. @harmoniclabs/crypto 0.3.1, BLS12-381. bls12_381_G1_uncompress / G2_uncompress accept x ≥ p (reduced mod p), where blst returns BAD_ENCODING. This is also a Plutus-builtin conformance issue.
  4. @harmoniclabs/crypto, missing pieces.
    • No blake2s; implemented in src/mithril/blake2s.ts.
    • No multi-scalar multiplication; Pippenger in src/mithril/bls.ts cut a 56-signer aggregation from 686 ms to 58 ms.
    • The package index is CommonJS and bundles every algorithm; src/mithril/hl.ts imports modules directly, 205 KB instead of 310 KB.
  5. @harmoniclabs/ouroboros-miniprotocols-ts 0.0.5-dev7, handshake.
    • HandshakeClient.propose(versionTable) never recognises a version table: isVersionTableMap checks the string keys of Object.keys with a number-only guard. It then throws VersionData :: invalid networkMagic: undefined.
    • The default proposal stops at version 14.
    • Gerolamino sends its own proposal (src/node/handshake.ts).
  6. @harmoniclabs/crypto 0.3.1, SHA-256 length. sha2_256_sync pads with a 32-bit bit-length; inputs over 512 MB hash incorrectly (preview tables is 650 MB). Gerolamino uses its own 64-bit SHA-256 (src/node/sha256.ts).

Roadmap

  1. Speed. Use @harmoniclabs/crypto's fast ed25519 port, and rebuild the VRF on the same curve code.
  2. N2N over WebSocket as a CIP. Write it from the server and client experience gathered here, so any node can serve Gerolamino peers; see WEBSOCKET_BEARER.md.
  3. Several peers and chain selection. Done 2026-10-23 (see "Not being fooled by peers").
  4. Volatile store. Done 2026-10-28 (see "Volatile store"): blocks within k slots of the tip stay in volatile files, promoted to immutable chunks as they age; rollbacks inside k touch volatile only.
